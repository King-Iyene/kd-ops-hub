# Rebuild KDOps automations on server events, not browsers

KDOps automations and webhooks should be rebuilt around one rule: **a Postgres trigger writes an event row in the same transaction as the record change, and server workers do everything else.** Today the browser fires automations after a save, so any edit from another user, the REST API, an import, SQL, or a closed tab is lost, and the runner trusts whatever the browser sends. The audit found **one problem verified live on 2026-11-23**: the `anon` role has SELECT, INSERT, UPDATE and DELETE privileges and allow-all policies on `nc_meta.automations` and `nc_meta.webhooks`. A fix is in PR #377. The other 14 problems below were read from code and migrations only; the live database was not inspected for them. The webhook delivery path (retry worker, backoff, replay, delivery ids) is sound and should be kept. The builder should stay a vertical step list with Airtable-style conditional groups, chips for dynamic values, and a test against one real record. The first release should ship the 12 triggers and actions in the ranked list in section A. Everything that touches the database or edge functions deploys to production on merge to `main`, so the build list in section F flags each such item for the owner's approval.

This report builds on two earlier documents and does not repeat them: `docs/database-structure-spec.md` and `docs/database-formula-links-research.md`. The structure spec's gap table marks automations as "Have" (its section 1, Automations). The audit below contradicts that for triggering, scheduling and security, so that row should be read as "UI exists, engine unsafe". The spec also notes that automations and webhooks do not fire for computed-column updates (its section 3.6), which the outbox design in section D must decide on explicitly.

## What is wrong today: 15 problems, ranked by severity

"Verified live" means checked against the production database; "code only" means read from source files or repo migrations, with the live state unknown. Severity is this report's judgement.

## A. Triggers and actions: twelve first, the rest later

Across Airtable, Notion, Baserow, NocoDB and the task tools, the common core is "record created", "field changed", a schedule, create/update record, notify or email, and a condition step. Airtable lists 10 trigger types and about 18 action groups ([Airtable](https://support.airtable.com/docs/getting-started-with-airtable-automations)); NocoDB lists 14 trigger nodes ([NocoDB](https://nocodb.com/docs/workflows/nodes/trigger-nodes)); Notion has four triggers and eight actions ([Notion](https://www.notion.com/help/database-automations)). Airtable's "record updated" watches chosen fields but does not check what they changed to, and bulk edits fire once per record ([Airtable](https://support.airtable.com/docs/when-record-is-updated-trigger)). Only NocoDB and, in effect, Notion offer value-aware triggers. The ranking below is an inference from cross-tool coverage and a recipe mapping (notify on status change, assign owner, create follow-up, copy to another table, due-date and invoice reminders, post to Slack or Sheets). No usage-frequency data was found.

| Rank | Item | Kind | Precedent | Note for KDOps |
|---|---|---|---|---|
| 1 | Record created | Trigger | All tools | Fires per record, including bulk and import |
| 2 | Field changed (field-selectable) | Trigger | Airtable, Baserow, Asana, Teable, NocoDB | Event carries `changed_fields` |
| 3 | Field changed to a value, with previous value | Trigger | NocoDB, Notion "is set to" | `old_record` token gives KDOps more precision than Airtable |
| 4 | Update record | Action | All | Must stamp `updated_by` and carry origin depth |
| 5 | Create record (including other table, linked) | Action | All | Header comment claims link support; code writes raw columns only |
| 6 | Send email | Action | Airtable, Notion | Fail the step when email is not configured; escape HTML; recipient allow-list |
| 7 | In-app notification | Action | Notion, ClickUp, Asana | Fail when recipients resolve to nobody |
| 8 | Scheduled (cron, timezone) | Trigger | Airtable, Notion, Baserow, NocoDB | Rows scanned by one cron tick |
| 9 | Find records, then for-each | Action | Airtable, Baserow | Needed for reminder recipes; cap iterations |
| 10 | Condition with Otherwise | Step | Airtable, Baserow Router, NocoDB If | Reuse the view-filter builder |
| 11 | Button clicked | Trigger | Airtable, Notion, NocoDB | Also the safe manual-run path |
| 12 | Send webhook | Action | Notion, NocoDB | Covers Slack and Sheets before native connectors; routed through the dispatcher |

Advanced, deferred: record-matches-conditions with re-entry semantics (already exists in KDOps and should be kept, since Airtable fires it each time a record changes into the matching state and not retroactively), enters-view, form submitted, inbound webhook (both exist in some form but are broken), delay beyond minutes, repeating groups and nested loops, run-a-script, multi-branch routers, "another workflow completes", native Slack/Sheets/Teams connectors, and quota dashboards. A date-relative trigger ("due date arrives", "N days before") is the friendlier form for small businesses and is used by ClickUp and Asana ([ClickUp](https://help.clickup.com/hc/en-us/articles/6312128853015), [Asana](https://help.asana.com/s/article/rule-triggers)); it can be built on the scheduled tick plus a date-field filter. Guard-rails worth copying: Notion forbids automations triggering automations and a recurring trigger cannot be combined with others, and it pauses an automation that errors after working ([Notion](https://www.notion.com/help/database-automations)).

## B. Builder UX: a vertical list with sentences, chips and a real-record test

**Layout.** Airtable, Baserow, Notion and NocoDB all use one trigger followed by ordered steps; Baserow and NocoDB configure a step in a right-hand panel ([Baserow](https://baserow.io/user-docs/workflow-automation), [NocoDB](https://nocodb.com/docs/workflows/create-workflow)). Canvases (Make, n8n, NocoDB) are reported to get confusing as workflows grow, and an n8n user reported a canvas pan change as an accessibility barrier (both from search snippets and forum posts, so weak evidence). With only one level of branching, a vertical list wins on scanning, keyboard order, phone width and screen readers; this is an inference, not a vendor statement. The recommended screen: header with editable name, generated sentence, enable toggle, Draft/Published badge, Test button and overflow menu (duplicate, history); a single column below with the trigger card, step cards joined by a "+" that opens a categorised add menu (Records, Notify, Logic); one card open at a time, each showing a one-line summary and a status chip (not configured, needs test, passed, failed) in text, not colour alone; drag handle plus keyboard move up/down. No source gave pixel sizes, spacing or icon sets, so those need design work.

**Conditional groups.** Copy Airtable's model: groups with a label, collapse, duplicate and delete; only the first matching group runs; an "Otherwise" group that is either additive or a catch-all; no nesting; 50 conditions per group; a warning when a group has no actions ([Airtable](https://support.airtable.com/docs/conditional-groups-of-automation-actions)). This replaces KDOps's `conditional` step, which has no else branch. Each condition row is field, operator, value, with a switch to "value from an earlier step", reusing the existing view-filter builder.

**Dynamic-value chips.** A "+ insert value" control opens a picker grouped by step, with the tested sample value beside each field name; the choice renders as a chip. NocoDB's chips offer List, Comma-separated, First item, Last item for list values, plus transforms such as Uppercase and Round ([NocoDB](https://nocodb.com/docs/workflows/create-workflow)); these map directly to link and multi-select fields. NocoDB offers values only after the producing step is tested, so sample data serves as the picker's schema. No source documents fallbacks, missing-value rendering, or a warning when an upstream field is deleted, so KDOps should specify its own: each chip shows an empty-value rule (blank, default text, or fail the step), and a chip whose field was deleted turns red and blocks publishing. Apply placeholders to every text field, including webhook URL, headers and create-record pairs, which today they skip.

**Testing.** Pick one real record once at the top and use it for every step; Airtable's inability to choose the record for action tests is the limitation to avoid ([Airtable](https://support.airtable.com/docs/getting-started-with-airtable-automations)). Test a step only after earlier steps have passing tests, and have Publish list the steps that fail validation (NocoDB). Baserow and Zapier tests act on live data ([Baserow](https://baserow.io/user-docs/workflow-automation)); none of the products checked documents a true dry run. A "preview what would change" mode, which evaluates conditions and placeholders and shows each write as a before/after diff without committing, is therefore an opportunity, though absence from the search is not proof of absence. KDOps's Test button must stop running real side effects by default.

**Templates and sentences.** monday.com's "When X, if Y, then Z" is the incumbent mental model ([monday](https://developer.monday.com/apps/docs/sentences), search snippet). A live sentence generated from the config doubles as the list-row summary. Start from a template gallery built from the recipes in section A, then a blank option. Draft/Published (Baserow) plus an enable toggle (Airtable, Notion) prevent half-built automations from running.

## C. Reliability and observability: one run per event, one row per step attempt

**Run history.** NocoDB logs inputs, outputs and status per step, each attempt and error, each loop item, masks credentials as `[redacted]`, and shows "Run by" for human-started runs ([NocoDB](https://nocodb.com/docs/workflows/execution-logs)). Its retry has four modes (failed step, failed step on the latest published version, continue a stopped run, rerun from start with the same trigger data), each creating a new run linked to the original. Airtable's rerun uses the configuration from the original attempt ([Airtable](https://support.airtable.com/docs/managing-airtable-automations)), and Zapier may block replay after significant edits (search summary), so KDOps must make "same version" versus "latest version" an explicit choice and store the definition version on every run. Filters to copy: status, date range, "Needs attention" (failed or stopped and not retried), "Retries only", "Slower than". Retention in peers runs from 2 weeks to 3 years by plan (Airtable figures come from a search snippet); KDOps should default to 90 days with a cleanup job. Mask secrets when writing, not when displaying.

**Retries and failure policy.** Retry only retryable errors (network, timeout, rate limit, 5xx), never permanent ones (bad configuration, missing field, auth, most 4xx); Make and Inngest both encode the split ([Inngest](https://www.inngest.com/docs/features/inngest-functions/error-retries/retries), [Make](https://help.make.com/incomplete-executions.md)). Retries are per step and skip completed steps, otherwise a retry repeats earlier side effects, a warning from Trigger.dev (search summary). The existing webhook schedule (1, 15, 60, 360 minutes, 5 attempts) is a reasonable default. Give each step an on-failure policy: stop the run (default) or continue. Auto-pause after repeated failure with one notification and explicit re-enable after a passing test: Zapier pauses at 95% errors over 7 days with 20 or more runs, Make after 3 consecutive errors by default, Baserow after roughly 5-10 ([Zapier](https://help.zapier.com/hc/en-us/articles/8496216132621), [Make](https://help.make.com/scenario-settings), [Baserow](https://baserow.io/user-docs/workflow-management)). Exclude handled errors from the count. Send failure emails to a short subscriber list; Airtable caps it at 10 owners or creators.

**Loop protection.** No vendor documents true dynamic cycle detection. NocoDB ignores a workflow's own changes and caps chaining at 3 levels, recorded as "Not run" ([NocoDB](https://nocodb.com/docs/workflows/execution-logs)); Airtable relies on advice plus auto-off for abnormal volume ([Airtable](https://support.airtable.com/docs/managing-airtable-automations)). Proposed KDOps rules (design inference): every automation-caused write carries `origin_run_id` and `depth`; depth above 3 produces a `skipped` run with reason `depth_limit`; a run's own writes to columns it watches are ignored; a per-automation circuit breaker (default 60 runs per minute) pauses and notifies. Allow chaining to depth 3, since today chained automations never fire.

**Limits.** Airtable caps runs per month, counts failed runs, and warns at 80/90/100% ([Airtable](https://support.airtable.com/docs/managing-airtable-automations)). KDOps is not billing runs, so the purpose is safety: per-automation runs per window, 25 steps per automation (Airtable's community-reported figure), 500 loop iterations (Zapier's cap, search summary), a per-run time budget, and queueing with a TTL instead of dropping over-limit events. Surface usage to admins.

**Idempotency.** Everything is at-least-once. Stripe and GitHub both recommend de-duplicating on a stable event id, signing with HMAC, and returning 2xx quickly ([Stripe](https://docs.stripe.com/webhooks), [GitHub](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks)). KDOps already has a stable delivery id for outbound webhooks. Add a unique key on (automation_id, event_id) for runs, a (run_id, step_index) key for steps, and send the step key outward as an idempotency header. Inbound webhooks store the provider's delivery id and reject repeats.

**Audit.** Record an actor per run (a user, or `system:automation:<id>`) and the run-as identity. Keep an append-only change log of definition edits, enable/disable, manual runs and retries. Scope run visibility by role: NocoDB lets owners and creators see all runs, editors only their own, and viewers none.

## D. Implementation on Supabase: outbox, workers, Vault, guarded fetch

**Event production.** pg_net sends HTTP after commit, but its queue tables are UNLOGGED (lost on crash), it documents no retries or delivery guarantee, and Supabase recommends at most about 200 requests per second ([pg_net](https://supabase.com/docs/guides/database/extensions/pg_net)). Database Webhooks wrap pg_net, document no delivery guarantee, and expose configured secrets in the trigger definition and in `net.http_request_queue` ([Database Webhooks](https://supabase.com/docs/guides/database/webhooks)). So pg_net may only wake a worker; the system of record is an event row written by an `AFTER` trigger in the same transaction as the change. The trigger should insert one small row and exit early when no enabled automation or webhook watches that table. Statement-level triggers with transition tables would handle bulk writes in one pass (design inference, not verified on Supabase here).

**Queue and workers.** Two options: pgmq, exposed as Supabase Queues, with visibility timeouts, `read_ct` and an archive table ([pgmq](https://github.com/pgmq/pgmq), [Supabase Queues](https://supabase.com/docs/guides/queues)); or a plain events table claimed with `FOR UPDATE SKIP LOCKED`, which KDOps's retry worker already uses. Recommendation: the plain table, because per-row status, tenant columns and the admin UI are simpler, and the claiming code already exists. pg_cron supports schedules down to seconds, recommends at most 8 concurrent jobs, and can call an edge function ([Supabase Cron](https://supabase.com/docs/guides/cron)). Run one tick (every 10-15 seconds) that claims a small batch and invokes the worker, plus the existing one-minute retry tick. Edge functions have a 150 s (free) or 400 s (paid) wall clock and 2 s CPU ([limits](https://supabase.com/docs/guides/functions/limits)), so a run is executed as short steps that persist progress, and a long delay is a stored `resume_at`, not a sleep.

**Proposed tables** (all in `nc_meta`; every row carries `base_id`; names are proposals):

| Table | Columns |
|---|---|
| `automation_versions` | `id`, `automation_id`, `version`, `definition jsonb` (trigger, steps), `created_by`, `created_at`, `published_at` |
| `automation_events` | `id` (the event id), `base_id`, `table_id`, `record_id`, `type`, `payload jsonb`, `origin_run_id`, `depth int default 0`, `batch_id`, `status` (pending, claimed, done, dead), `attempts`, `next_attempt_at`, `claimed_until`, `created_at` |
| `automation_runs` | `id`, `automation_id`, `version_id`, `event_id`, `base_id`, `actor`, `status` (queued, running, waiting, retrying, succeeded, failed, stopped, skipped), `skip_reason`, `trigger_snapshot jsonb`, `parent_run_id`, `is_test`, `resume_at`, `started_at`, `finished_at`, `error_summary`; unique (`automation_id`, `event_id`) |
| `automation_run_steps` | `id`, `run_id`, `step_id`, `attempt`, `status`, `input jsonb`, `output jsonb` (masked, size-capped), `error_class` (retryable, permanent), `error`, `duration_ms`, `idempotency_key`; unique (`run_id`, `step_id`, `attempt`) |
| `webhook_endpoints` | existing webhooks table plus `secret_ref` (Vault id, replacing the plaintext column), `header_secret_refs`, `pending_cap`, `consecutive_failures`, `paused_reason` |
| `automation_change_log` | `id`, `automation_id`, `actor`, `action`, `before jsonb`, `after jsonb`, `created_at` |

**Event shape** (JSON in `automation_events.payload`; one event per record, never `{count}`):

```json
{ "event_id": "uuid", "type": "record.updated", "base_id": "...", "table_id": "...",
  "record_id": "...", "occurred_at": "...", "actor": {"user_id": "...", "source": "ui|api|import|automation|form|sql"},
  "record": { }, "old_record": { }, "changed_fields": ["status"],
  "origin": {"run_id": null, "depth": 0}, "batch": {"id": "...", "index": 3, "size": 40} }
```

Types: `record.created`, `record.updated`, `record.deleted`, `form.submitted`, `button.clicked`, `schedule.due`, `inbound.webhook`. For `record.deleted`, include the full old row, not just the id. Workers re-read the current row server-side instead of trusting any client payload, but keep the snapshot for history.

**Step types:** `update_record`, `create_record`, `find_records` (with `for_each` as a child list, capped), `condition_group` (ordered branches plus otherwise), `send_email`, `notify`, `send_webhook`, `delay` (`resume_at`), `log`, `stop`. Each has a pure `validate(config)` and a pure `render(config, context)` so both can be unit tested.

**Security.** Run the worker with service role only for engine tables; before any record write, re-check that the automation's owner still has write access to the base (design inference; Supabase's RLS-versus-service-role behaviour was not fetched). Move secrets to Vault, which encrypts at rest and exposes plaintext through `vault.decrypted_secrets` to anyone with access to that view, so restrict it; a plain dump and restore cannot decrypt Vault secrets without the root key ([Vault](https://supabase.com/docs/guides/database/vault)). The browser then sees only "secret set" and a rotate button. The memory index notes the repository is public with unencrypted dumps (from project memory, not verified here), which raises the stakes of keeping secrets out of migrations. Build one shared outbound-fetch module used by the dispatcher, retry worker, replay, runner and proxy. OWASP's rules: allow https only, reject userinfo and parser-ambiguous URLs, resolve DNS and check every A and AAAA result, connect to the validated IP while keeping the hostname for SNI and certificate checks, disable redirects, apply the same policy to retries, and canonicalise IPv4-mapped and NAT64 addresses before checking ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)). Whether Deno's `fetch` on Supabase can pin a resolved IP is unknown; if it cannot, an egress proxy is the fallback. Add a short timeout, a response-read cap and truncated stored bodies (these three are recommendations without a source). Baserow's separate flags for webhooks and its HTTP action ([Baserow community](https://community.baserow.io/t/webhook-to-device-on-local-network-not-working-even-after-setting-env-variable/5193)) show why the policy belongs in one module. Sign every outbound request with HMAC-SHA256 over `timestamp.body`, send `X-KDOps-Timestamp` and an idempotency key, keep a per-endpoint secret with a rotation overlap (Stripe keeps the old secret active up to 7 days). Inbound: keep the constant-time HMAC check, add a 5-minute timestamp window, a body-size limit, delivery-id de-duplication and a real record id instead of `webhook-${Date.now()}`.

**How others do it.** n8n's queue mode keeps pending execution ids in Redis and results in the database, with workers pulling ids and a default concurrency of 10 ([n8n](https://docs.n8n.io/hosting/scaling/queue-mode/)). Baserow, NocoDB and Grist fire webhooks from the application layer after a change, keep call logs, and cap or clear queues; Baserow caps 5,000 pending calls per webhook on Cloud and handles them one at a time ([Baserow](https://baserow.io/user-docs/webhooks)); Grist batches rows into one array payload and has a Clear Queue button ([Grist](https://support.getgrist.com/webhooks)). None uses database triggers. Worth copying for bulk edits: batched payloads and per-endpoint pending caps.

**Migration plan** (each stage its own branch, per the repo rules): (1) add tables and corrected RLS, with the trigger writing events and nothing consuming them; (2) shadow mode, logging what the server path would fire beside the browser path; (3) consume server-side for flagged tables, with the unique key preventing double-fire during overlap; (4) remove browser invocation; (5) move secrets to Vault; (6) enable the scheduled tick. Risks: double-fire during overlap, write amplification on hot tables, loops, backlog if workers stall (monitor oldest pending event age), and the 2 s CPU limit for heavy transforms.

## E. The current state worth keeping

Keep `webhook-dispatcher`, `webhook-retry-worker` and `webhook-replay`: every attempt is stored in `webhook_deliveries`, a pg_cron worker runs each minute with a `SKIP LOCKED` claim, backoff is 1, 15, 60 and 360 minutes over 5 attempts, delivery ids are stable, manual replay exists, and an endpoint auto-disables after 10 exhausted failures with 50 deliveries kept per webhook (all code only; the auto-disable function's own comment admits it may never have fired). Keep `verifyInflowSignature` (fails closed, constant-time compare) and the false-to-true transition tracking for `record_matches_conditions`. Everything else in problems 1-15 is rebuilt or fixed. The structure spec's migration `20261222400000_automation_runs_and_scheduler.sql` is named as read in that spec; the audit says no cron calls the runner, so the first task of the scheduler work is to read that migration and the live `cron.job` table to see what exists.

## Decisions the owner must make

1. Approve the order: security fixes (items 1-5) before any new feature, accepting that existing secrets move to Vault.
2. Confirm the outbox must also fire for REST API writes, imports and automation-made writes, or limit it to UI edits first. This changes every user's experience, including silent firing for old imports.
3. Choose the plain events table with `SKIP LOCKED` or pgmq.
4. Decide the run-as identity: the automation owner, the triggering user, or a dedicated limited role. Owner-as-run-as is simplest but needs a re-check of the owner's access on every run.
5. Set defaults: depth limit (proposed 3), runs-per-minute breaker (60), consecutive failures before auto-pause (5), run-history retention (90 days), step cap (25).
6. Decide who may create and edit automations (all base editors, or owners only) and who may see run history.
7. Accept or reject a rule that a failed email or notification fails the run, which will expose runs that "succeeded" before.
8. Decide whether private-network webhook targets are ever allowed (NocoDB and Baserow use an environment flag for this), and whether an egress proxy is acceptable if Deno cannot pin IPs.
9. Decide how to treat existing rules with `scheduled` or `webhook_inflow` triggers that never ran: migrate as paused, or ask each owner.
10. Decide whether the legacy browser path is removed at stage 4 or kept as a flagged fallback, which keeps double-fire risk alive.

## What is not verified

All figures marked as search snippets or summaries (Airtable plan quotas and retention, Zapier retries, retention and loop cap, Pipedream, Make, Trigger.dev, Temporal, NocoDB community-edition limits) were not checked on the vendor pages, and Airtable limits conflict between sources: automations per base is 75-200 on the fetched page versus 50 in a search summary, and the 25-actions-per-automation and script time limits are community-reported. No source gave pixel specs, fallback behaviour for dynamic values, a dry-run implementation, or dynamic cycle detection. On Supabase, the beta or GA status of Queues, Realtime delivery guarantees, `FOR UPDATE SKIP LOCKED` semantics (from training knowledge, no page read), edge function payload limits, pinned-IP `fetch`, throughput of the outbox trigger, and RLS-versus-service-role behaviour were not verified. The Baserow technical page returned 404, so its retry defaults and Celery use are unconfirmed; NocoDB and Grist retry schedules were not found. For KDOps, the live database was inspected only for problem 1; the deployed edge-function code, `cron.job` state and the contents of migration `20261222400000` were not read in this research.

## Conclusion

The central finding is that the order of work matters more than the feature list. Three of the four critical problems are about who may touch automations, not about what they do, and a server-side trigger turns each of them into a larger exposure, so the authorization and secrets work has to come first. The second finding is that the best-in-class bar is lower and more specific than "match Zapier": a single trigger, a short list of steps, Airtable-style branch groups, one run row per event with per-step attempts, explicit retry modes, and a depth cap. Several of those (retry modes linked to the original run, a self-write filter, an empty-value rule on every chip, and a dry-run diff) are things the peers either skip or leave undocumented, so a small team can exceed them at modest cost. The unproven parts are all on the Supabase side, which is why the migration plan runs the server path in shadow mode before it replaces the browser.
